- Обидва запускалися в окремих Node `24.21.0` процесах; джерело — поточний локально налаштований Lviv GTFS provider у loopback БД `marshgo`. - Це не frozen-feed benchmark: файл фіда не фіксувався за SHA в цьому діагностичному прогоні. Його не можна використати як оцінку p95/p99 або гарантію на інші дні.

## Висновок

- PR #28 показав відтворюваний напрямок зниження пікової пам'яті для цього запиту, не змінивши зафіксований порядок 100 результатів у другій парі.
- Обидві реалізації повернули 100 маршрутів із `searchTruncated=true`. Це лише memory optimization і regression parity, не усунення truncation, не доведення оптимальних переможців трьох режимів і не staging/production acceptance.
- Provider feed identity/bytes не зафіксовані, тож для релізного performance твердження потрібен повторний A/B на SHA-піннутому frozen feed із щонайменше п'ятьма окремими процесами на варіант і p50/p95/RSS summaries, плюс перевірка exact FASTEST/CHEAPEST/BALANCED winners.
- PR #28 залишається відкритим. Жодних файлів/контейнерів/даних під час цього вимірювання не видаляли.
