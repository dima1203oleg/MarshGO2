## Завершено в цьому фрагменті

1. У [production completion ТЗ](../PRODUCTION_COMPLETION_TZ_2026-10-18.md) додано обов’язковий цикл реалізації, перевірки, виправлення й переходу до наступного P0/P1, а також checkpoint для безпечного відновлення після переривання.
2. Server зіставляє provider-scoped GTFS ID маршруту/рейсу з сирими ID VehiclePositions; зберігає окремий provider stop ID для точки посадки.
3. Journey live API приймає `legId`, повертає точні напрямки статичної лінії та всі свіжі GPS-позиції її provider+route. Геометрію малюємо лише з `shapes.txt` GTFS; пряму між зупинками не видаємо за точну лінію. До трьох машин акцентуються тільки за збігом поточного trip, service date/route та прогресу до boarding stop. Невідомий напрямок або stale GPS не отримують статусу «наближається».
4. Site запитує live контекст після вибору сегмента; флот малюється одним GeoJSON-шаром із транспортними піктограмами. Якщо feed не має точної повної геометрії, UI прямо повідомляє, що лінію не домальовує. Камера не повторює наближення на кожному опитуванні.
5. Вибір segmentId з картки/стрічки/лінії синхронізований. На карті весь ланцюг лишається видимим: вибраний відрізок має акцент, інші відрізки приглушені, а зупинки обмежені вибраним етапом і спільними точками пересадки. Фокус не змінює маршрутні дані. Hit-testing використовує окрему ширшу зону; неоднозначні близькі лінії пропонують вибір. Тест покриває збереження геометрій повного маршруту й dimmed/selected стани.
6. Production-збірка явно запускається з `NODE_ENV=production`; перевірено, що результат містить production React runtime. Для браузерних сценаріїв використовується окрема збірка в `/tmp`, щоб інтеграційний runner випадково не перевіряв або не перезаписував stale `dist`.
7. Додано API integration test для live overlay: автентифікація обов’язкова, доступ лише власнику маршруту, `legId` обмежує вибір сегмента, вимкнений провайдер повертає явний `UNVERIFIED/provider_unavailable` без ліній і маркерів. Тест використовує loopback test DB; його URL навмисно не звертається до зовнішнього джерела.
8. У мультимодальному пошуку однакові запити метро до станцій тепер кешуються тільки на час одного запиту, з обмеженням до 128 записів і ключем із координат/часу/провайдера. Результат пошуку, що обрізався внутрішнім бюджетом, тепер піднімає `candidateGenerationTruncated`; API не видає такий результат за повний. Додані тести на повторне використання, різні ключі й межу кешу.

## Продовження 2026-10-18: ціни, метро GeoJSON і ізольований пошук

1. Для маршрутів із велосипедом/самокатом агрегована ціна тепер лишається `UNKNOWN` (`totalPriceMinor`, min/max і currency — `null`), доки немає повної орендної пропозиції. `maxPriceMinor` відсікає такі кандидати замість порівняння лише з тарифом метро. Тариф підтвердженого transit-сегмента може бути показаний окремо зі своїм статусом.
2. Live journey overlay приймає геометрію маршруту з офіційного Kyiv Metro GeoJSON лише коли провайдер явно позначив її provenance `official_geojson`; GTFS shapes лишаються `gtfs_shape`. Геометрія без provenance не приймається. GeoJSON geometry повертає статус `SCHEDULED` без GPS-маркерів — фактичний рух не вигадується. Додано 2 перевірки цього правила.

## Продовження 2026-10-18: згода й foreground GPS зустрічі

1. Додана міграція `054_rendezvous_participant_consent.sql` з окремими timestamp-згодами водія й пасажира. Старий `location_sharing_enabled=true` не вважається доказом згоди: міграція вимикає попередній обмін і скидає обидва consent timestamps. Міграція застосована тільки до loopback `marshgo_e2e` через штатний integration runner; звичайну локальну БД, staging і production не змінювали.
2. Endpoint активації тепер лише готує сесію; він сам не вмикає GPS. Новий `POST /api/v1/rendezvous/:id/consent` приймає згоду окремо від кожного автентифікованого учасника підтвердженого бронювання. Обмін активується лише коли є обидві згоди. Учасник без власної згоди отримує `403 location_consent_required`; відкликання вимикає sharing і видаляє обидві ephemeral точки. При новій парі згод очищаються старі Redis точки, а timestamp перевіряється, щоб попередня сесія не «ожила».
3. Site прибрав одноразову кнопку відправлення координати й запускає `watchPosition` тільки після двох згод і лише на відкритому екрані. Передача throttled: не частіше 10 секунд, якщо позиція не змінилася щонайменше на 20 м; неточність понад 100 м відкидається. Відмова/помилка GPS зупиняє watch і намагається відкликати згоду. При виході компонента watch зупиняється. Background iOS tracking ще не реалізований/не перевірений.
4. API integration test тепер перевіряє блок до згоди, що одна згода не вмикає sharing, двосторонню доставку тільки після згоди обох, свіжість координат, два ручні arrival confirmations, boarding gate та відсутність координат у постійних event metadata. Повний isolated `npm run test:integration` пройшов 29/29; Server `npm test` — 213 passed, 0 failed, 1 opt-in skipped; typecheck і lint пройшли. Site — 89 passed, typecheck/lint/build пройшли.
5. Порти test API `3306/3307/3308` після прогону закриті. Site `4301` та локальний API `3002` повертають `/healthz` HTTP 200. API `3002` не перезапускався, тож новий Site-клієнт не перевірявся браузером із новим серверним consent migration; не застосовував міграцію до робочої БД для такого тесту.

### Що ще не завершено для GPS-зустрічі

- У нижній картці ще немає спільної інтерактивної карти з двома позиціями та двома окремо розрахованими маршрутами/ETA до точки pickup. Зараз видно статус/свіжість іншого учасника, але не map overlay.
- Немає UI acceptance з двома незалежними браузерними сесіями, перевірки permission denied/reconnect і підтвердження авто-зупинки watcher на реальному WebKit/iPhone.
- Capacitor iOS нативний Core Location bridge для background/lock-screen не доведений. Потрібні фізичний пристрій і TestFlight acceptance.
- Після кодових змін server треба безпечно прогнати migration на окремому staging та перевірити дві клієнтські сесії; тільки тоді оцінювати продакшн.

Ролі маркерів визначаються відносно поточного користувача. UI явно повідомляє, що маршрути й ETA до посадки не розраховані; прямі лінії між GPS-точками не малюються.
- GPS watcher лишається лише для авторизованої сесії, видимої вкладки, активної зустрічі та двох згод. При переході у фоні watcher зупиняється; terminal states не показують учасницькі координати.
- Додано unit-тести для авторизації/видимості/згод/термінальних станів та побудови набору точок для карти (включно з відсівом stale і координат без згоди). Це не замінює перевірку двох незалежних браузерних клієнтів.
- Останній повтор Site: `npm test` — 94/94, typecheck — успішно, lint — успішно, production build — успішно, bundle budget — успішно (17 JS chunks не більше 350 KB gzip), `npm audit --omit=dev --audit-level=high` — 0 вразливостей. `git diff --check` — чистий. Локальні Site/API `4301/3002` відповіли HTTP 200 на `/healthz`.
- Оновлений браузерний acceptance саме для картки зустрічі не виконаний: у відкритій вкладці пошук маршруту, підтвердженої зустрічі немає. Двосторонні маршрути й ETA до pickup не реалізовані, бо немає підтвердженого пішохідного роутера для кожного учасника; навмисно не підміняються прямою лінією. Не перевірені реальні GPS-дозволи/відмови на двох незалежних клієнтах, iOS/TestFlight, staging міграція та production smoke. Реліз не розгортався.
- Повторний Playwright route-map acceptance на актуальному Site bundle пройшов: сегментна картка, перемикання світлої/темної теми, всі висоти нижньої панелі, порядок зупинок, фокус сегмента, видима камера, контекст повного маршруту в панелі й навігаційні шари перевірені. У E2E assertion прибрано помилкову вимогу приглушених інших сегментів: canonical `SEGMENT_FOCUS` показує лише вибраний етап на карті, повний ланцюг лишається в панелі.
- Існуючі Playwright screenshots для route results, light/dark route sheet і навігації оновлені після перевірки зміненої touch-ієрархії карток та пройшли повторний run без `--update-snapshots`. Три ключові кадри (результати, світла розгорнута карта, темна розгорнута панель) переглянуті вручну; решта кадрів пройшли pixel comparison у runner.
- Фінальний root `npm run check:production` пройшов: typecheck, lint, 232 тести (1 opt-in DB integration test пропущений), production build і bundle budget (51 JS chunk до 350 KB gzip). Це локальні гейти; production deployment/smoke не виконувалися.
- Ще раз виконано root `npm run test:integration`: 30/30 успішно (journey schema, booking/trip editing, rendezvous bilateral consent/location, foreground navigation, Redis realtime між двома API, restart durability, shared rate limit). Скрипт ізолювався на loopback `marshgo_e2e` і виставив `MOBILITY_ROUTING_FEEDS_DISABLED=true`; його mode matrix показала лише fixture-попутку, а міські transit/bike/scooter гілки були blocked. Тому цей run доводить інтеграційні контракти, а не актуальне міське покриття.
