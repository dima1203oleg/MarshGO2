# Порівняння GTFS-пошуку між Server release-кандидатом і локальною гілкою — 2026-10-21

## Мета

Перевірити, чи можна вважати локальну Server-гілку `feature/transport-layer-availability` еквівалентною інтегрованому release-кандидату Server PR #21 перед подальшим перенесенням коду.

## Джерела й метод

- Release baseline: чистий Server checkout PR #21, SHA `cbf17c2ccf05d7a7e3126fa0caf74ef8049bc7a2`.
- Локальне дерево: гілка `feature/transport-layer-availability`, HEAD `182c77ae4f78d576a287007d8e0864fb130f43f8`, плюс 30 pre-existing modified/untracked paths. Жодної з цих змін benchmark не редагував.
- GTFS: один і той самий локально збережений статичний архів Львова; SHA-256 `bb4ac0ce9127b4967ad889379f523b04b84a0bb033814aa8c844526b42078164`. Живі позиції, staging і виробничий API не використовувалися.
- Чотири однакові OD-коридори, вікна відправлення 30 або 90 хвилин, до 3 пересадок, ті самі walk-shed/transfer bounds і результатний ліміт 100. Майбутній час відправлення зафіксовано від часу запуску. Baseline і локальний код запускалися почергово по три рази; route ID набори в кожному варіанті були детерміновані.
- Виконання: Node `25.4.0` (вимога репозиторію `24.21.0`), один процес. Це діагностичний A/B між двома різними source revisions, не ізольований benchmark одного патча й не production capacity test.

## Результати

Усі запуски повертали 100 результатів і позначали пошук обрізаним. Відомий мінімальний тариф був `2300` для кожного коридору, тому цей feed не розрізняє стратегію найдешевшого маршруту.

Послідовності результатів двох версій не збігалися в жодному коридорі: кожен набір мав 100 доданих і 100 відсутніх ID. Кожний з чотирьох локальних запитів був приблизно швидшим у цьому запуску, але швидкість супроводжувалася суттєвою зміною пропозиції маршрутів; у двох коридорах зникли всі прямі маршрути, а в двох інших direct-count зменшився. У центр→вокзал найкращий час погіршився на 460 секунд. Це не можна прийняти як загальне покращення.

## Аналіз і рішення

Гілка `feature/transport-layer-availability` є предком release-кандидата, але не еквівалентним його станом. Порівняння source показує, що PR #21 має суттєвіші bounded/query-directed GTFS retention та transfer-feasibility правила; локальний код також має коротший вибір зупинок. Отже, локальну гілку не можна механічно просувати як заміну PR #21. Часові показники не приписуються окремій зміні, бо source revision і робочі зміни різні.

**Рішення:** не cherry-pick/merge-ити незбережений локальний GTFS-код у release-кандидат на підставі швидкості. Зберегти існуючі зміни недоторканими. Перш ніж використовувати будь-який код з локальної гілки, потрібне контрольоване порівняння на одному й тому самому базовому commit із перевіркою, що fastest/direct feasible routes, обов'язкові пересадки та strategy winners не зникають. У PR #21 пошук також лишається bounded/truncated і потребує окремого рішення щодо повноти.
