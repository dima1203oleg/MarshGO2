Повернуто 100 маршрутів і 35 різних послідовностей назв маршрутів. `candidateGraphTruncated=true`, `candidateSamplingTruncated=true`, `searchBudgetTruncated=true`, `searchTruncated=true`, `resultLimitReached=true`.

- Для контексту той самий запит без явної 6-годинної межі використав дефолт 24 години: попит 1,147,651, 98,418 утриманих сегментів, 46,738 кроків, 33 ланцюги й ~2.60 с. Це не міський API default.

## Висновок та наступна технічна дія

Поточна проблема походить насамперед із графового обмеження: навіть при реальному 6-годинному горизонті оцінений попит перевищує 100-тисячну межу у 4.37 раза. Збільшення глобального чи per-route cap створить суттєво вищі витрати пам’яті; історичні cap/reservoir sweep-и вже не дали надійного приросту покриття. Тому наступна робота має перевірити інший пошуковий підхід, який не materialize-ить кожну пару зупинок: bounded label/Pareto або timetable/route-pattern search з точними transfer rules. Він має збігтися з exhaustive tiny-feed oracle для набору feasible маршрутів і переможців FASTEST/CHEAPEST/BALANCED до будь-якого A/B на реальному фіді.

**Статус:** повнота львівських маршрутів не пройдена; сервер правильно повідомляє неповноту. Це не staging чи production acceptance; release status лишається `NOT_RELEASED`.
