# Повторна read-only перевірка львівських GTFS-Realtime фідів — 2026-10-21

## Зріз

Перевірено приблизно о 16:40 UTC прямими HTTPS GET до публічних endpoint-ів:

- `https://track.ua-gis.com/gtfs/lviv/vehicle_position`
- `https://track.ua-gis.com/gtfs/lviv/trip_updates`

| Фід | HTTP | Прочитано | Заголовок фіда | Вміст |
|---|---:|---:|---:|---|
| Vehicle Positions | 200 | 63,079 байтів | приблизно 3 с | 604 позиції; 503 мали timestamp віком до 90 с; 0/604 повідомили `currentStopSequence`; повтор production-декодером о 16:41 UTC: 602 розібрано, 501 свіжий, 0 sequence |
| Trip Updates | 200 | 209,987 байтів | приблизно 18 с | 657 TripUpdate записів; protobuf декодувався успішно |

О 16:41 UTC окремий повтор VehiclePositions пройшов через production decoder `parseGtfsRealtimeVehicles()` з Server PR #23: 602 позиції розібрані, 501 timestamp свіжий до 90 секунд, `currentStopSequence` явно присутній у 0 позицій. Кількість природно змінилася між snapshot-ами; декодер зберіг усі валідні координати, не синтезувавши stop progress.

Перший запит Trip Updates у тому самому короткому вікні повернув HTTP 200 і 208,921 байт, але protobuf-декодер отримав помилку індексу за межами буфера. Повтор одразу після цього декодувався успішно з іншим розміром 209,987 байтів. Це один короткий збій читання/цілісності під час live probe, а не доказ постійної недоступності фіда. Production-клієнт має трактувати помилку декодування як невдале оновлення й залишати schedule fallback, не позначати дані як live.

## Що це означає для карти

- Позиції транспорту були свіжими в момент зрізу й можуть підтримати приглушені live-маркери після коректного зіставлення з лінією/рейсом.
- Жодне з 604 повідомлень позиції не мало явно переданого `currentStopSequence`. Декодований protobuf може повертати для відсутнього числового поля значення за замовчуванням; воно не є доказом прогресу. Server PR #23 зберігає sequence лише за фактичної наявності поля.
- На підставі цього фіда зараз не можна достовірно виділити конкретні 2–3 транспортні засоби як такі, що прямують до обраної зупинки, і не можна обіцяти ETA на основі цього sequence. UI має залишити їх без акценту та явно не називати прогноз підтвердженим.
- 657 TripUpdates не доводять, що координати кожного транспортного засобу можна точно зв'язати з потрібним рейсом/напрямком. Цей зріз не виконував повторного зіставлення зі static GTFS і не перевіряв маршрут у staging.

## Межі доказу

Це один read-only мережевий зріз публічних даних. Він не доводить SLA, безперервну свіжість, ліцензійну/операційну угоду, production API поведінку, ефективність polling-кешу, staging UI або готовність до production. Декодер-помилку першого TripUpdates запиту слід врахувати в спостереженні за якістю upstream; потрібні повторювані спостереження та безпечний schedule fallback.

Кандидат Server на час повторної перевірки: PR #23 SHA `1ab6034348a8e48adca0c46df472273054eb023f`. Точні push/PR CI runs `39636489795` і `39636499906` пройшли, включно з PostgreSQL/Redis integration. Злиття, staging та production deployment не виконувалися.
