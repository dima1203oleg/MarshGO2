## Пам'ять

Окреме вимірювання в кожному процесі з `--expose-gc`:

- до розбору: RSS приблизно 137–147 МБ;
- після розбору ZIP/GTFS: RSS приблизно 568–576 МБ;
- після GC після розбору: RSS приблизно 548–557 МБ, heap близько 140 МБ;
- після одного пошуку та GC результатів: RSS приблизно 696–806 МБ, heap близько 142 МБ.

Окремі стадії пошуку показали близько 98,4–98,6 тис. створених сегментів при оціненому попиті понад бюджет 100 тис.; граф обрізається. Одночасний прогін п'яти запитів в одному процесі дав близько 1,20 ГБ RSS, але це включає повторні пошуки без рестарту процесу, тому не є оцінкою пам'яті одного запиту. Потрібен окремий контрольований тест сервісу з паралельністю й профілем пам'яті Node 24.21.0.

## Рішення та наступний крок

- Не змінювати caps за цими даними: попередні A/B відхилили прості зміни бюджету та кількості зупинок через втрату швидких/Pareto-кандидатів.
- Відкрите питання: чи утворюється велика тимчасова пам'ять при побудові stop-pair сегментів, чи довго живуть індекси/кеші між запитами, чи обидва чинники. Далі потрібні профіль одного пошуку та контрольована послідовність повторів на Node 24.21.0; паралельний тест — лише в ізольованому локальному середовищі.
- Docker daemon зараз недоступний (`unix:///Users/dima1203/.docker/run/docker.sock`), тому локальний Postgres/PostGIS/Redis тест не виконано. Compose-файли перелічують призначені сервіси, але активні контейнери та їх restart policy не підтверджені.
- `docker-compose.yml` визначає локальні `db` (PostGIS 17/3.5), `redis` 7.4 та `s3mock` 5.2.2; `ops/staging/docker-compose.yml` визначає окремі staging PostGIS, Redis і object storage. `compose.production.yml` описує production-служби, але сам файл не доводить, що production розгорнутий.
- Жоден контейнер не запускав, не зупиняв і не змінював. Статус релізу лишається `NOT_RELEASED`.

## Повтор на зафіксованому Node 24.21.0

Node 24.21.0 відтворено тимчасовим `npx --package=node@24.21.0`; package files і lockfile репозиторію не змінювалися. У п'яти окремих процесах результати, кількість сегментів за ланцюгом і truncation flags збіглися з попереднім Node 25.4.0 прогоном. Часи: 2 490, 2 782, 2 400, 2 044, 2 370 мс; медіана 2 400 мс. RSS після GC після розбору фіда: 489–504 МБ; після одного пошуку: 644–732 МБ; heap після GC: приблизно 141–149 МБ.

У повторному тесті п'яти пошуків в одному Node 24.21.0 процесі з примусовим GC між ними heap після кожного пошуку тримався приблизно 142–143 МБ. RSS виріс від ~504 МБ після розбору до ~686 МБ після першого пошуку, далі стабілізувався в діапазоні ~712–727 МБ. Це не показує необмеженого зростання heap у цьому синтетичному повторі, але не замінює heap snapshots, load test, вимірювання без примусового GC чи паралельного навантаження. Усі п'ять результатів лишилися обрізаними.
