# Перевірка вибраного сегмента громадського транспорту й live-флоту

**Час перевірки:** 2026-10-20 00:16 Europe/Kyiv (2026-10-19 21:16 UTC)  
**Мета:** звірити канонічний сценарій вибору автобуса/маршрутки на карті з кодом, тестами та поточним львівським фідом.  
**Статус приймання:** частково підтверджено; production/staging не перевіряли.

## Висновок

Поведінка карти, яку описав власник, уже реалізована в робочому кандидатові Site PR #11 (`5879adad41ef03a17d07da144c1fae7bbd97d62a`) і серверному шляху live-journey в Server PR #12 (`4a9015c476cc8ead44617c4544456a5cbf1a8f06`). При виборі розкладного сегмента Site приховує інші планові сегменти саме з карти, лишає вибраний кольоровий сегмент, завантажує контекст повної лінії обох напрямків і розміщує свіжі машини цієї лінії. Інші етапи залишаються у списку маршруту.

Сервер бере напрямки з GTFS-геометрії з підтвердженим походженням, відбирає свіжі машини точного оператора та `route_id`, і підсвічує не більше трьох тих, чий trip ID, service date і послідовність зупинок підтверджують рух до зупинки посадки. Якщо цього доказу немає, машина може залишитися приглушеною, але не отримує вигаданий статус «їде до посадки». Site малює повний лінійний контекст із низькою прозорістю, машини без пріоритету — приглушено, підтверджені наближення — яскраво.

Поточний live-зріз Львова не дає машин: обидва доступні GTFS-RT джерела відповіли валідним порожнім protobuf із нулем машин, trip updates та alerts. Тому коду й fixture-тестів достатньо, щоб підтвердити механіку, але не для заяви про фактично робочий live-флот на цей момент.

## Відкриті вимоги

1. Повторити маршрутний live endpoint на актуальному налаштованому provider record у тестовій БД/стейджингу, щоб підтвердити справжній шлях API → GTFS/GTFS-RT → UI. Сам факт, що статичний catalog feed доступний, не доводить, що provider увімкнений у середовищі.
2. Для live-парку потрібні непорожні свіжі GTFS-RT позиції з `route_id`, `trip_id`, датою/напрямком і current stop sequence. Поточний львівський probe їх не надав.
3. Для обох повних ліній потрібна геометрія вибраного `route_id` із точними напрямками. Якщо доступний лише довірений geometry одного сегмента, не видавати його за повну лінію в обох напрямках.
4. Повторити ізольований staging E2E з живим API/провайдером. Поточний Site E2E — фікстурний, хоча запускався на production UI у трьох браузерних рушіях.
5. Після staging повторити зріз у робочий час і звірити freshness, кількість машин, `route_id`, обидва напрямки та фактичні 0–3 наближення. Кількість може бути нуль, коли feed не передає придатні машини.

**Production стан:** NOT_TESTED. Немає підтвердженого production host/deployed SHA; ця перевірка не є дозволом на production rollout.
